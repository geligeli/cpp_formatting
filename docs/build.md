# Build configuration, toolchain and dependency hygiene

Part of the maintainer notes indexed by [AGENTS.md](../AGENTS.md).

## Bazel configuration (.bazelrc)

- All builds pass `--cxxopt=-fno-rtti` (required when linking against LLVM/Clang libraries built without RTTI).
- **The C/C++ toolchain on Linux is [hermetic-llvm](https://github.com/hermeticbuild/hermetic-llvm)** (`bazel_dep(name = "llvm")`, a prebuilt Clang 23 with compiler-rt, libc++, libunwind and the libc built from source -- no compiler, sysroot or standard library comes from the machine). See "C/C++ toolchain" under "Build files" for what that changed. It is what makes remote execution sound: a worker and a workstation produce the same bytes.
- `bazel build --config=minify-x86_64 //cpp_formatting:cpp_format` (or `minify-aarch64`, from either kind of host -- the toolchain cross-compiles, and the release workflow builds both on x86_64 runners) produces the release binary: size-optimized (LTO, section GC, stripped) and **fully statically linked against glibc**. Static is a property of the target *platform* (`//tools/platforms:linux_<cpu>_glibc_static`), which is why there is one config per CPU; plain `--config=minify` is the shared flag set and links dynamically. Nothing is needed on PATH. `//code_browser:code_browser` is the other release binary and builds under the same configs: `minify` turns exceptions off globally, Boost.Asio reports every error by throwing, so `--per_file_copt=external/boost\..*,code_browser/.*@-fexceptions` gives them back to exactly those files (a per-file copt lands after every `--cxxopt`, and the last `-f[no-]exceptions` wins). LLVM, protobuf and abseil stay without, so their objects are shared between the two binaries in one release build; nothing throws *through* them -- the frames between Asio's throw and `http_server`'s catch are Boost's and code_browser's own.
- `bazel test --config=asan //...` (likewise `tsan`, `ubsan`) runs the tests under a sanitizer. **Everything in the target configuration is instrumented, LLVM included** -- most of what these tools can get wrong is a lifetime error on something of Clang's, and the faulting access is then as likely to be inside LLVM as in our code -- so the first build under each config is a from-source LLVM build; each has its own `--platform_suffix` (`bazel-out/k8-fastbuild-asan`, …; no leading dash, Bazel adds one), so switching configs evicts nothing, and the exec-configuration tools are shared and uninstrumented. `-O1 -g1` rather than fastbuild's `-O0`: instrumented `-O0` LLVM is too slow for the rename tests, and `-g1` symbolizes a report without multi-gigabyte objects. Four things are specific to the hermetic toolchain, each found by a failing link:
  - **The switch is the toolchain's (`--@llvm//config:asan`), not `--copt=-fsanitize=address`.** There is no prebuilt sanitizer runtime to link; the switch builds compiler-rt's from source and adds the flags itself -- to everything *except* its own startup files and runtimes. A `--copt` reaches those too, and lld then rejects the instrumented `crtend.o` (`a section asan_globals with SHF_LINK_ORDER should not refer a non-regular section`). Linux only, like the toolchain.
  - **RTTI is on (`build:sanitizer --cxxopt=-frtti`).** The normal build is `-fno-rtti` only to match LLVM's, and here LLVM is compiled in the same configuration, so there is nothing to match. It is mandatory under ASan: without RTTI Clang emits a private *weak* copy of the typeinfo of every type a TU throws (`std::bad_function_call`, `bad_variant_access`, …), the instrumented libc++ defines the same typeinfo *strongly* inside a COMDAT group of the same signature, and lld refuses the mix (`relocation refers to a symbol in a discarded section: typeinfo for …`). Small tests that throw none of those types link fine, so a spot check does not find this -- only the whole suite does. With RTTI on, `ubsan` no longer disables `vptr`.
  - **`test:sanitizer --build_tests_only`.** `//...` holds `//tools/gazelle`, a Go program whose C link step gets the sanitizer runtime but not libunwind (`undefined symbol: _Unwind_Resume`).
  - **`ubsan` switches nothing off any more.** The three null checks (`null`, `nonnull-attribute`, `returns-nonnull-attribute`) were off because any of them makes *GCC* drop `-fdelete-null-pointer-checks`, after which abseil's `&function == nullptr` in a `constexpr` does not compile; the toolchain is Clang now. `-fno-sanitize-recover=all` stays, without which a finding is a line on stderr and a passing test.

  - **TSan tests run on the local machine (`test:tsan --modify_execution_info=TestRunner=+no-remote-exec`).** Compiling remotely is fine; *running* is not: on a kernel with high mmap entropy a TSan binary re-executes itself with ASLR off, which a remote worker's container does not allow (`FATAL: ThreadSanitizer: encountered an incompatible memory layout but was unable to disable ASLR`), and whether it needs to depends on where the kernel happened to map things -- a flake, not a failure.

  All three configs pass the whole suite. The first complete `tsan` run under Clang found two real races in `code_browser`'s HTTP server that GCC's had never reported (see "`code_browser`" in [source-map.md](source-map.md)). A sanitizer runtime cannot be linked into a static executable, so `//tools/platforms/smoke`'s tests are incompatible with a sanitizer configuration and are skipped there (a `config_setting_group` over the toolchain's `*_enabled` settings, in the BUILD file; the transition itself may not name `@llvm` -- see "A consumer loads every package" in [integration.md](integration.md)). The first `asan` run (under GCC) is what found the two zlibs (see "One zlib"). There is still **no `msan` config**, but the reason has changed: it needed an instrumented libc++ and a toolchain switch, and the hermetic toolchain has both (`--@llvm//config:msan`); it has simply not been tried here.
- **`bazel coverage //...`** needs no config: the `coverage` lines in `.bazelrc` apply to that command only. The LCOV report is `bazel-out/_coverage/_coverage_report.dat` (per test: `bazel-testlogs/<pkg>/<test>/coverage.dat`); `genhtml` from lcov turns it into HTML where it is installed (it is not part of the build). It covers `//cpp_formatting` and `//code_browser`, leaving out their `tools/` test helpers (`http_get`, `apply_patch`). Four things were needed on top of `--combined_report=lcov`, each found by an empty or wrong report:
  - **Clang's source-based coverage (`--experimental_use_llvm_covmap --experimental_generate_llvm_lcov`).** Without it Bazel compiles gcov-style (`-fprofile-arcs`), and the collector then wants a `gcov`.
  - **The tool paths come from `--test_env`.** Bazel 8's built-in `cc_test` reads `llvm-profdata` / `llvm-cov` only from a toolchain's legacy `tool_paths`, which hermetic-llvm (a rules-based toolchain) leaves empty, so `collect_cc_coverage.sh` died on `COVERAGE_GCOV_PATH: unbound variable` after the tests passed, and every report was empty. The rc names both binaries by exec path in the toolchain's repository (`COVERAGE_GCOV_PATH` is the *profdata* tool, which is what bazel_tools' collector merges with). The repository name has no version in it but does have the exec CPU (`-linux-amd64`), so this works on x86_64 only, like CI and the RBE workers. The better fix is `cc_legacy_tool`s in the hermetic-llvm fork (rules_cc 0.2.25 has `cc_toolchain(legacy_tools = …)`), or Bazel 9, whose rules_cc `cc_test` falls back to the action configs' tools.
  - **The toolchain's coverage feature is off (`--features=-llvm_coverage_map_format`); the flags are per file instead.** `--instrumentation_filter` decides what gets *reported*, not what gets compiled with counters. The feature puts `-fprofile-instr-generate -fcoverage-mapping` on every compile in the configuration (only the gcov format is gated, on a per-target variable). So LLVM, protobuf, zlib, Boost and sqlite all carried counters -- over a thousand LLVM and Clang files in each binary's coverage map, bumped non-atomically from the TU driver's worker threads. A per-file `-fno-profile-instr-generate` cannot undo that, because the rules-based toolchain appends feature flags *after the source file*, behind every copt. So `--per_file_copt=^(//)?(cpp_formatting|code_browser)[/:]@-fprofile-instr-generate,-fcoverage-mapping,-fprofile-update=atomic` instruments exactly the two packages, and `--linkopt=-fprofile-instr-generate` pulls in the profile runtime. A per-file regex is matched against the source's **label as well as its path**, and the pattern spells both. Because LLVM's compile commands are now the same as a plain `bazel test`'s, coverage reuses its objects.
  - **`-fprofile-update=atomic`.** The TU driver's workers and the browser's `io_context` threads race on the counters. llvm-cov works out many line counts by subtracting one counter from another, so lost increments showed up as negative counts (`invalid number on DA line DA:281,18446744073709551577`), and the coverage merger dropped those lines.

  What it collects, and one warning to ignore:
  - **Subprocesses.** The shell integration tests and `smoke_test` get their coverage entirely from child processes, since the test itself is a script. Every process writes its own `.profraw` (`LLVM_PROFILE_FILE=…/%h-%p-%m.profraw`, inherited through the environment), and the collector gives llvm-cov every binary in the test's `data` as an `-object` (the `runtime_objects_list.txt` of each). So a new test needs nothing special, as long as the binary it runs is in its `data` and in the target configuration. The binaries the `//bazel/testdata` tests check ran *during the build*, as aspect actions in the exec configuration, so they contribute nothing.
  - **Continuous mode (`-fprofile-continuous`, `--test_env=LLVM_PROFILE_CONTINUOUS_MODE=1`).** Normally a process writes its counters from an `atexit` handler, so one that never reaches `exit()` -- `SIGKILL`ed, crashed, leaving through `_exit()` as a gtest death test's child does -- contributes nothing. That was measured: a `code_browser` server `SIGKILL`ed after one request left no file at all. With the counters kept in the mmapped `.profraw` itself (bazel_tools' collector appends the `%c` the mode needs), the same run gives 135 lines of `http_server.cpp`. Today's tests stop the server with `SIGINT`, which its `signal_set` turns into a normal return from `main`, so this changes no number yet. It keeps a future test from silently losing a child's coverage. The flag only has to be on the compiles.
  - **"warning: N functions have mismatched data" is expected** (231 in `smoke_test`, a few elsewhere). Every one has `hash = 0x0`: Clang writes a zero-hash "unused function" record for each inline function a file sees but does not call (here protobuf's and abseil's header code, `index.pb.h` accessors). When some other file did call it, the profile has that name under its real hash, so llvm-cov skips the unused record with this warning. The counts from the file that called it are still reported. `llvm-cov report -dump` lists them.

  Coverage is not a separate output tree (no `--platform_suffix`); only our own sources and the links differ from a `test` build.
- **Tests that parse C++ fixtures get their standard library from the toolchain ([tools/hermetic_std/](../tools/hermetic_std/)).** A fixture that says `#include <coroutine>` is resolved by the Clang driver *inside the test process*, which looks where a Clang on that machine would -- `/usr/include`, the installed libstdc++, and for `<stddef.h>` GCC's builtin directory, since the in-memory helpers pass no `-resource-dir`. The tests therefore passed on a workstation and failed on a remote-execution worker whose image has no C++ headers (8 cases of `rename_variables_test`), *intermittently*, depending on which side of a dynamic-execution race won. `HERMETIC_STD_DATA` / `HERMETIC_STD_ENV` hand the four fixture-parsing `cc_test`s and the return-type integration test five directories through `CPLUS_INCLUDE_PATH`, which the driver searches before its defaults: the toolchain's libc++ and libc++abi, **Clang 21's own builtin headers** (collected into one directory by `header_directory`; a builtin header belongs to the compiler doing the parsing, not to the toolchain's Clang 23), the kernel's and glibc's. The check is `bazel test //... --spawn_strategy=remote --test_tag_filters=-local`, which passes. The package is separate from `//cpp_formatting` because it names `@llvm`, a dev dependency no consumer can see.

## Code style

- C++ formatting is enforced by `clang-format` (Google style, see [.clang-format](../.clang-format)) via the pre-commit hook in [.pre-commit-config.yaml](../.pre-commit-config.yaml): `clang-format -i -style=file` on all `*.h`/`*.cpp` files.
- The same file runs three more hooks, in this order (`pre-commit install` once; `pre-commit run --all-files` by hand): **`iwyu`** (`tools/iwyu/iwyu.sh check` — check only, because its edits want review; the first run builds IWYU, `SKIP=iwyu git commit` gets past it), **`gazelle`** (`bazel run //tools/gazelle`, fixing in place like clang-format: a changed BUILD file stops the commit, `git add` lets it through) and **`buildifier`** (`-mode=fix -lint=off` on every BUILD/MODULE/`.bzl`/`*.BUILD`, last so it also formats what Gazelle wrote; the binary is pinned in the devcontainer). The two Bazel hooks take no file names — Bazel knows what changed — and their `files:` patterns only decide *whether* they run. Each was checked to fail on a dropped dep, a misformatted rule and a dropped include respectively.

## Includes and dependencies (include-what-you-use + Gazelle)

Two tools keep the dependency graph a function of the code, and they run in this order: IWYU makes every file include exactly what it uses, then Gazelle derives every `cc_*` target's deps from those includes.

```
tools/iwyu/iwyu.sh check                  # what IWYU would change; exit 1 if anything
tools/iwyu/iwyu.sh fix                    # apply it (fix_includes.py + clang-format), then review the diff
bazel run //tools/gazelle                 # rewrite deps / implementation_deps from the #includes
bazel run //tools/gazelle -- -mode=diff   # the CI gate: print the diff, exit 1 if there is one
tools/gazelle/llvm_index.sh               # after an LLVM bump: regenerate the LLVM header index
```

- **Gazelle** ([tools/gazelle/](../tools/gazelle/)) is [gazelle_cc](https://github.com/EngFlow/gazelle_cc). `gazelle` and `gazelle_cc` are **dev dependencies**, and the `gazelle`/`gazelle_binary` targets are reached through `//tools/gazelle` rather than the root package for the same reason (they are *aliases* there, to rules instantiated in the dev-only `@gazelle_runner` repository -- a `load()` from `@gazelle` would stop the package loading for a consumer; see "A consumer loads every package" in [integration.md](integration.md)): this module is imported by URL by kit consumers, who must get neither rules_go in their module graph nor a root BUILD file that loads from a repo they cannot see (verified against a `local_path_override` consumer). The configuration is the `# gazelle:` directives in the root [BUILD.bazel](../BUILD.bazel) — comments, so harmless in a dependency. What they encode:
  - `cc_group unit` — one library per header/source pair, the layout the packages already had.
  - `exclude` for `bazel/testdata`, `cpp_formatting/testdata`, `e2e`, `third_party`: fixtures whose exact shape is asserted by tests, and vendored build files.
  - `cc_indexfile tools/gazelle/llvm.ccindex` — gazelle_cc resolves external headers through an index of BCR modules, and `@llvm-project` is not one (it comes from the module extension). [tools/gazelle/llvm_index.sh](../tools/gazelle/llvm_index.sh) derives the header → label map from the overlay's own `cc_library` rules with one `bazel query` and checks it in, one header per line; a header several libraries list goes to the one with the fewest headers, so the file is deterministic and Gazelle never reports an ambiguity.
  - `resolve_regexp cc ^google/protobuf/ @protobuf//:protobuf` — the built-in index names protobuf's internal sub-packages for some headers and knows nothing for others (`message.h`).
  - `resolve cc gtest/gtest.h @googletest//:gtest_main` — no `#include` names `gtest_main`, so a generated dep list would lose every test's `main()`; `gtest_main` exports `gtest`.
  - `cc_unresolved_deps error` — an include nothing resolves fails the run instead of silently dropping a dep.
- **What Gazelle needs from a BUILD file**, each learned from its first dry run: a `package(default_visibility = …)` (without one gazelle_cc makes every library it touches public); `# keep` on a generated source listed by label (`:clang_include_headers_embed_cc`, the `web_*_cc` genrules — a comprehension it cannot read); and **a binary named after its source file** — existing `cc_binary` rules are matched by name only, so `code_browser`'s `main.cpp` became `code_browser.cpp` (it would otherwise have grown a second binary called `main`), and `tools/http_get.cpp`, a source in a sub-directory of `//code_browser`, became the package `//code_browser/tools`.
- **`implementation_deps`** — gazelle_cc puts a dependency only a library's `.cpp` includes into `implementation_deps`, so the BUILD files now say which deps a library re-exports. The repo's own aspects had to learn the attribute (see "`implementation_deps`" in [integration.md](integration.md)).
- **IWYU** ([tools/iwyu/](../tools/iwyu/)) is built from source against the repo's own Clang: `@iwyu` is pinned next to `LLVM_VERSION` in [third_party/llvm/extensions.bzl](../third_party/llvm/extensions.bzl) because an IWYU release supports exactly one Clang release (0.25 ↔ Clang 21) — **bump them together** — with [third_party/iwyu/iwyu.BUILD](../third_party/iwyu/iwyu.BUILD) standing in for its CMake build. [tools/iwyu/iwyu.bzl](../tools/iwyu/iwyu.bzl) is an aspect in the shape of `cpp_format_aspect` (one cached action per file, the compile command Bazel derives, `-resource-dir` for the staged builtin headers, a per-target manifest so a stale report is never read); [tools/iwyu/iwyu.sh](../tools/iwyu/iwyu.sh) is a plain script for the reason `cpp_format.sh` is. It analyses every TU plus every header no TU of the same stem accompanies — IWYU reports a main file *and its associated header* (`foo.cpp` and `foo_test.cpp` both → `foo.h`). Not in CI: its suggestions want review, and it links an LLVM code generator. The non-obvious parts:
  - **`--no_fwd_decls`.** The code base is Google style (include, do not forward-declare). Without the flag IWYU forward-declares first-party types throughout the headers (`enum class OutputMode;`, `class Repo;`), and an include that is not there is a dependency edge Gazelle cannot see.
  - **LLVM/Clang/protobuf include directories are passed as `-I`, not `-isystem`.** IWYU spells a suggestion by how the compile command reaches the header, and Bazel puts every external `includes = [...]` behind `-isystem`, so it wrote `<clang/AST/Decl.h>` where the code writes `"clang/AST/Decl.h"`. That is not cosmetic: IWYU decides whether the *associated header* already provides an include by comparing spellings, so every `.cpp` was told to repeat what its own `.h` includes. Rewriting the quotes afterwards cannot fix that; presenting the directory as a quoted one does.
  - **[tools/iwyu/mappings.imp](../tools/iwyu/mappings.imp)** — every entry is a suggestion nobody should follow, with the reason: libstdc++ 15 symbols IWYU 0.25 finds at a forward declaration (`std::pair` in `<iterator>`, `std::vector` in `<format>`), LLVM detail headers, Beast behind its two umbrella headers, Asio's `impl/` files mapped **one by one** to the public header that declares the same function (a blanket mapping to some other header makes IWYU call the right include unused — it removed `co_spawn.hpp`), abseil reached only through protobuf's JSON API.
  - **The standard library is the hermetic toolchain's libc++, and two things follow.** (1) `_is_quoted_include_dir()` must not match the toolchain's repositories: one of them is *also* named `llvm-project` and holds libc++ (`external/llvm++llvm+llvm-project/libcxx/...`), so the `+llvm-project/` test demoted the C++ library itself to `-I` -- IWYU then spelled it `"string"` and, no longer recognising it as the C++ library, recommended its implementation headers (106 files flagged). A canonical repo name starts with its module's, so any path component beginning `llvm+` is left behind `-isystem`. (2) libc++ 23 is newer than the mappings IWYU 0.25 ships, and it splits every public header into dozens of private ones (`<__fwd/string.h>`, `<__utility/move.h>`). [tools/iwyu/libcxx.imp](../tools/iwyu/libcxx.imp) maps all ~900 of them to their public header; it is **generated** by [tools/iwyu/gen_libcxx_mappings.py](../tools/iwyu/gen_libcxx_mappings.py) from libc++'s own module map (`module string { module fwd { header "__fwd/string.h" } header "string" }`), with a short table for the implementation headers several public ones share (`<__tree>` → `<set>`/`<map>`). Regenerate it after a toolchain bump. The handful of *symbol* mappings libc++ needs are in `mappings.imp`. One include changed for real: a `std::map` iterator's `operator!=` lives in `<map>` under libc++ (libstdc++ keeps it in a tree header `<set>` also provides), so `const_placement_lib.cpp`, which walks `Rewriter`'s buffer map, now includes `<map>`.
  - **`<stddef.h>` → `<cstddef>` is done by `fix`, not by a mapping** — IWYU's built-in choice among a symbol's providers cannot be reordered, but it accepts the C++ spelling once it is there, so the rewrite is a fixpoint.
  - **`fix_includes.py` is line-based.** It took the `#include <compare>` inside a raw-string fixture in `trailing_return_types_test.cpp` for the file's include block and edited the fixture. Look at the diff of any test that embeds C++ source.
  - IWYU instantiates more than a compile does, which found one real defect: `IndexDb() = default;` in the class body needs `~unique_ptr<Connection>` on an incomplete type (GCC never instantiated it). It is now defined in the `.cpp`, next to the destructor.

## Build files

- [cpp_formatting/BUILD](../cpp_formatting/BUILD) — Defines all `cc_library`, `cc_binary`, `cc_test`, and `sh_test` targets, plus the `clang_include_headers` `pkg_tar` and the `clang_include_headers_embed_cc` `genrule` that embeds the headers into every binary.
- [MODULE.bazel](../MODULE.bazel) — Bzlmod dependencies: `rules_cc`, `googletest 1.15.2`, `rules_shell`, `rules_pkg`, `protobuf 31.1` (the symbol index format — `proto_library`/`cc_proto_library` are loaded from `@protobuf//bazel:…`; 31.1 rather than the 29.0 the graph used to resolve transitively because 29.0's abseil pin, 20240116.1, does not compile under GCC 15 and 29.0 references an abseil target the fixed releases removed, so the pair moves together), plus `bazel_skylib`, `platforms`, `rules_python`, `apple_support` (needed by the LLVM overlay's BUILD files). `zlib` is a direct dependency because the `llvm` extension's `llvm_zlib` repo is a shim over it (see "One zlib" under "Clang/LLVM from source"). `llvm` is the hermetic C/C++ toolchain, taken through an `archive_override` from a fork that can link glibc statically (see "C/C++ toolchain"); it, `gazelle` and `gazelle_cc` are `dev_dependency = True` (the latter two for BUILD file maintenance, see "Includes and dependencies"); `@iwyu` comes from the `llvm` extension. Clang/LLVM (21.1.8) is **not** a BCR dependency — the Bazel Central Registry only publishes llvm-project up to 17.0.4 — so it is built from source via a local module extension (see below).

### C/C++ toolchain: hermetic-llvm, and glibc linked statically ([geligeli/hermetic-llvm](https://github.com/geligeli/hermetic-llvm), branch `glibc-static`)

Two things are called LLVM here and they are unrelated: `@llvm` is the **toolchain** (the BCR module `llvm`, hermetic-llvm 0.8.21: a prebuilt Clang 23.1 whose runtimes and libc are built from source), and `@llvm-project` is the Clang 21.1.8 **library** source the tools link (next section). The first compiles the second.

- **Registration is Linux-only and dev-only.** `MODULE.bazel` registers the four `@llvm//toolchain:linux_{x86_64,aarch64}_to_linux_{x86_64,aarch64}` toolchains rather than `@llvm//toolchain:all`: macOS and Windows keep the toolchain Bazel finds on the machine (`.bazelrc`'s `build:windows` block is written for `cl.exe`, and neither host has been validated against the hermetic one). The `stage1_*`..`stage3_*` toolchains in that package bootstrap the compiler from source and are not needed. Both the `bazel_dep` and the registration are `dev_dependency = True` -- a consumer importing the kit by URL keeps their own toolchain.
- **What moving off GCC + libstdc++ changed.** (1) LLVM 21's `RDFRegisters.h` specializes `std::less<RegisterRef>` with a data member, and libc++ 22+ `static_assert`s that a `std::less` specialization used by an associative container is empty, so `llvm:CodeGen` did not compile: [patches/llvm_rdf_std_specializations.patch](../patches/llvm_rdf_std_specializations.patch) backports upstream's fix (a558d656, #160804) minus its unit-test hunk -- drop it with the bump to LLVM 22. (2) The sanitizer configs use the toolchain's switches (`--@llvm//config:asan`), see `.bazelrc`. (3) `//bazel/testdata:compile_commands_test` is tagged `local`: the database's `directory` is the *execution root*, and under a sandbox or on a remote worker only the test's declared inputs exist beneath a directory of that shape. It used to pass because `.bazelrc` says `--spawn_strategy=local`; a user rc that turns on remote/dynamic execution overrides that, and **dynamic execution then needs `--dynamic_local_strategy=sandboxed,local`** -- with `sandboxed` alone no strategy is left that may run a `local` action and Bazel refuses the test.
- **Static glibc is built from source, by a fork of the toolchain.** hermetic-llvm links glibc the way `zig cc` does: against stub `.so` files generated from a symbol list, the implementation coming from the machine the binary runs on. There is no `libc.a`, so `--features=fully_static_link` (what `--config=minify` used to rely on, with a system Clang and the system's `libc.a`) fails with `unable to find library -lc`. The toolchain's own static story is musl, which was tried and works, but musl's allocator is slow under threads and `--jobs` is allocation-heavy. So `MODULE.bazel` takes the module from the fork through an `archive_override` -- upstream's release tag plus the `glibc-static` branch, as a hash-pinned tarball (not `git_override`: no git needed on the machine, and it lands in the repository cache). It began as three patches under a `single_version_override`, 4 MB of them in this repo; the fork exists because the generator scripts were text inside a patch that could not be run without applying it, and because the feature is of use to other repositories. What the branch adds, all under `3rd_party/libc/glibc/static/` there:
  - **The build is transcribed, not ported.** glibc has no build description but its makefiles, which decide what to compile through `sysdeps` directory ordering, `Implies` files, generated makefile fragments and a configure run. `reference_build.sh` runs glibc's own `configure && make V=1` with the toolchain's Clang in a throwaway container (glibc 2.43+ builds with Clang on exactly x86_64 and aarch64), and `gen_manifest.py` reduces the log to (a) `<arch>/manifest.bzl` -- for every object of `libc.a` and `libm.a`, its source and exact flags, with the build's directories replaced by `{src}`/`{gen}`/`{sub}` placeholders and the ~45 shared sysdeps `-I` directories folded into one `@INCLUDES` entry -- and (b) `<arch>/gen/`, the files of the *build* tree those compiles read (`config.h`, `abi-versions.h`, the gen-as-const offset headers, and the ~130 syscall stubs make pipes into the assembler, materialized as `.S` files). Everything else is the pristine release tarball hermetic-llvm already fetches. Which archive a member belongs to is decided by byte-comparing against the reference archive, since members are basenames and glibc builds some basenames twice.
  - **`glibc_static.bzl` replays the manifest**, one action per object (~3100 on x86_64, ~2700 on aarch64; about half a minute on the cluster), under the toolchain's *stage0* transition -- a libc cannot be compiled by a toolchain that links it. The exported symbols of the result are identical to the reference build's (4792 in `libc.a`, 2019 in `libm.a`). Two details: the generated tree is put *first* on the include path, because hermetic-llvm patches an **empty** `include/config.h` into its glibc repository for the crt objects and `<src>/include` is glibc's first `-I` (no file name exists in both, so nothing else is affected); and kernel and installed-glibc headers arrive as `-isystem` from `CcInfo` deps, after every `-I`, because glibc's internal headers wrap the installed ones with `#include_next`.
  - **Static mode is a constraint, `@llvm//constraints/glibc_linkage:static`, not a flag.** A Starlark flag would reach the exec configuration, whose platform is glibc 2.28, where the 2.44-only target is incompatible -- every build tool would break. A platform constraint exists only on the target platform. It adds the archives to the glibc library search directory (next to the stubs: a `-static` link looks for `lib*.a` only, so they never compete; `libpthread.a`/`libdl.a`/`librt.a` are empty since 2.34 but every link line names them), turns on the same `static_link_executable` args musl uses, and **swaps all four startup files for glibc's own**: the toolchain's `crt1.o` has no `static-reloc.o` (the stub of `_dl_relocate_static_pie` a non-PIE static link needs -- `undefined hidden symbol: _DYNAMIC`), its `crti.o`/`crtn.o` are compiled from an empty file while `libc.a`'s `__libc_start_main` calls the `_init`/`_fini` they define, and only glibc has an `rcrt1.o` for `-static-pie`.
  - **The glibc version is part of the platform** (`parents = ["@llvm//platforms:linux_<cpu>_gnu.2.44"]`): the program must be compiled against the public headers of the `libc.a` it links. Unlike the dynamic stubs' 2.28 this is not a compatibility floor -- a static binary carries its libc; the floor is the kernel (`--enable-kernel=4.19`).
  - [tools/platforms/smoke/](../tools/platforms/smoke/) is the regression test: `for_platform_test` transitions one program to the static platform inside the ordinary `bazel test //...` (the aarch64 one is skipped on an x86_64 host and vice versa). The program checks TLS, threads, libm, exception unwinding and -- through `getauxval(AT_BASE) == 0` -- that no dynamic loader was mapped; built dynamically the same program fails, which is what makes it a test. The release binary was also run in an Alpine container (no glibc on the machine) and the aarch64 build under `qemu-user`.
  - What static glibc cannot do is unchanged from any distribution's: NSS, iconv and `dlopen` load shared objects at run time. The tools use none of them.
  - The branch also makes one existing thing public, `@llvm//runtimes/glibc:kernel_headers_include_search_directory`, next to the glibc one that already was: `//tools/hermetic_std` has to name the sysroot's directories itself.
  - **The generated data is reproducible and half dead weight removed.** `reference_build.sh` runs with `CFLAGS=-O2` because two generated files are compiler *output* and with glibc's default `-g` carried DWARF naming the build's directories; `first-versions.h`/`abi-versions.h` -- shared-library symbol-version tables, 43% of the data -- are one-line stubs, which was verified, not assumed: every object and startup file is byte-identical with the real tables (without `SHARED`, `SHLIB_COMPAT()` is the constant 0). Regenerating from a fresh reference build reproduces the checked-in bytes.
  - **Bumping hermetic-llvm** means rebasing `glibc-static` onto the new upstream tag (the change is additive but for one `select` in `runtimes/BUILD.bazel`), tagging it `v<upstream>-glibc-static.<n>`, and changing `integrity`/`strip_prefix`/`urls` in `MODULE.bazel`. **Bumping the static glibc** means `reference_build.sh` + `gen_manifest.py` per architecture and `GLIBC_STATIC_VERSION`, in the fork.

### Clang/LLVM from source ([third_party/llvm/](../third_party/llvm/))

The BCR tops out at llvm-project 17.0.4, so to track a newer Clang (21.1.8, needed for C++23 features like deducing `this`) the project pulls LLVM's own Bazel overlay (`utils/bazel`) from the monorepo source instead of a BCR module.

**Why 21.1.8 and not something older.** 19.1.7 aborts on abseil's `absl/log/log_format_test.cc` with an assertion inside Clang's own Sema (`ExprClassification.cpp`, `` `isLValue()` ``), reached while instantiating a local variable whose initializer needs a user-defined conversion. It is Clang's bug, not ours — it reproduces with an empty ruleset, so with none of this project's visitors or matchers running — and it took abseil out of the e2e corpus entirely. Only assertion-enabled builds hit it (`-c opt` compiles the assertion out), which is why released binaries were never affected but the fastbuild dev loop was.

- [third_party/llvm/extensions.bzl](../third_party/llvm/extensions.bzl) — a Bzlmod `module_extension` (`llvm`) that `http_archive`s the pinned `llvm-project` source (`llvm-raw`), `llvm_zstd` and `iwyu`, defines `llvm_zlib` (a shim, below), then runs `llvm_configure` to generate the `@llvm-project` repo. Only the `X86` and `AArch64` targets are registered (the tools just need the host target for a `TargetInfo`; the release workflow ships x86_64 and aarch64 Linux binaries -- both built on x86_64 runners, the aarch64 one cross-compiled by the hermetic toolchain -- plus an aarch64 macOS one), which keeps the from-source build small. Bump `LLVM_VERSION`/`LLVM_SHA256` here to change the Clang version.
- **One zlib.** The overlay links `@llvm_zlib//:zlib` into `llvm:Support`, and upstream's recipe for that repo is a private copy of zlib-ng in zlib-compat mode. protobuf links the BCR `zlib` into the same binaries (`gzip_stream`), so `cpp_format` — the shipped one — carried two libraries exporting the same symbols, the winner of each decided by link order. It worked because the two are API-compatible and one happened to win every symbol. AddressSanitizer reports it as an ODR violation on `deflate_copyright` before `main()` runs, which is how it was found: five tests, exactly the gtest binaries that link protobuf, died at startup on the first `--config=asan` run. `llvm_zlib` is therefore a generated repo holding one **`alias`** to `@zlib` (which resolves through this module's repo mapping, hence the `bazel_dep`). An alias and not a `cc_library` wrapping it, which is what it was for one push: `llvm:Support` includes `<zlib.h>`, and under Clang's `layering_check` the target it depends on must be the one that *owns* the header — a wrapper fails with `does not directly depend on a module exporting 'zlib.h'`. **GCC has no layering check, so the devcontainer's `bazel test //...` cannot see this class of error; every release build is Clang and all four failed.** An alias cannot carry the `LLVM_ENABLE_ZLIB=1` define upstream's zlib target exported, so [patches/llvm_enable_zlib_define.patch](../patches/llvm_enable_zlib_define.patch) adds it to the overlay's `llvm_config_defines` — it replaces `llvm_zlib_std_c11_msvc.patch`, which patched the zlib-ng build file nothing uses any more. Check after touching any of this: `CRC.pic.o` must still have an undefined `crc32` (zlib support is on), and `bazel build --config=minify //cpp_formatting:cpp_format` is the local stand-in for the release jobs.
- [third_party/llvm/configure.bzl](../third_party/llvm/configure.bzl) — vendored copy of the upstream overlay rule. One local change vs. upstream: `_extract_cmake_settings` resolves the CMake files by a plain repo-root-relative path instead of `Label("//:...")`, which is a self-reference that fails to package-load under Bazel 8 + Bzlmod while the repo is still being fetched.
- [MODULE.bazel](../MODULE.bazel) — wires it up via `use_extension` + `use_repo(llvm, "llvm-project", ...)`.

## Patches

The `patches/` directory holds patches applied to the LLVM source at fetch time, listed in the `llvm-raw` `http_archive` in [third_party/llvm/extensions.bzl](../third_party/llvm/extensions.bzl). Of the four applied ones, two keep zstd and blake3 building under MSVC, `llvm_enable_zlib_define.patch` declares zlib support in the overlay's config defines (see "One zlib") and `llvm_rdf_std_specializations.patch` is an upstream backport libc++ needs (see "C/C++ toolchain"); `llvm_smallvector_cstdint.patch` is unused, having gone obsolete with the LLVM 19 upgrade (upstream `SmallVector.h` now includes `<cstdint>` itself). Other MSVC breakage is handled with conformance flags in [.bazelrc](../.bazelrc) rather than by patching LLVM — see `/Zc:preprocessor` and `/permissive-` there. Clang/LLVM is built from source via the module extension in [third_party/llvm/](../third_party/llvm/); see the "Clang/LLVM from source" section above.
